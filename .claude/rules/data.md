# Rule: Data

- The real, authoritative schema is the DDL itself: [src/HrAutomation.Infrastructure/Database/scripts/03-create-tables.sql](../../src/HrAutomation.Infrastructure/Database/scripts/03-create-tables.sql) (tables), `04-create-keys-indexes-constraints.sql` (keys/FKs/indexes), `07-create-stored-procedures.sql` (the procedures that own workflow-critical writes). Inspect these — and the actual live schema via `sqlcmd`/SSMS — before adding or changing an entity; do not assume [docs/03-data/data-dictionary.md](../../docs/03-data/data-dictionary.md)/[er-diagram.md](../../docs/03-data/er-diagram.md) reflect it — both carry an "Implementation reality notice" marking them as the original target-state design, since the real system diverged (see [ADR-006](../../docs/adr/ADR-006-database-first-stored-procedure-workflow.md)).
- Every table carries `TenantId`, a `UNIQUEIDENTIFIER` primary key, `CreatedAtUtc`/`UpdatedAtUtc`, `CreatedByUserId`/`UpdatedByUserId`, and — for mutable entities — `RowVersion` (`rowversion`, optimistic concurrency) and `IsDeleted` (soft delete). Follow the pattern already used throughout `03-create-tables.sql`, not [docs/03-data/sample-relational-schema.sql](../../docs/03-data/sample-relational-schema.sql) (a Postgres-dialect illustrative sample, not the real schema).
- There is no generic `workflow_state_transition`/workflow-engine table. Each entity's status lives on its own column (e.g. `recruitment.JobRequisition.RequisitionStatusCode`), and the stored procedure performing a transition enforces the current-status precondition atomically with the write — see [ADR-006](../../docs/adr/ADR-006-database-first-stored-procedure-workflow.md) before adding a new workflow.
- C# access to `HrAutomationDb` follows `src/HrAutomation.Infrastructure/Persistence/README.md`: simple CRUD/single-aggregate reads through `HrAutomationDbContext` (EF Core, database-first); multi-entity, security-sensitive, or workflow-critical writes through the matching stored procedure via `StoredProcedureExecutor`, never hand-rolled multi-statement LINQ.
- Any schema change is a versioned, additive-first migration to the real DDL scripts above (plus a matching seed-script update if reference data is affected) — do not drop a column/table in the same release that stops writing to it. `docs/03-data/database-migration-strategy.md` describes the general principle; it predates the real migration mechanism (hand-written, numbered SQL scripts, not EF Core migrations).
- Never store a compensation figure as free text; reference the external compensation system by ID. (No offer/compensation flow is implemented yet — this rule applies when that work starts.)
- Never index raw candidate identity documents or confidential interview feedback into the vector store by default — see [ADR-003](../../docs/adr/ADR-003-rag-and-vector-store-boundary.md). (No vector store integration exists yet — `HrAutomation.Rag` is an empty scaffold.)
- Retention/deletion logic must respect legal hold and the categories in [docs/03-data/data-classification-and-retention.md](../../docs/03-data/data-classification-and-retention.md) — never hard-delete without checking hold status first. No automated retention/purge process is implemented yet.
- The audit log (`audit.AuditEvent` table, plus `audit.SecurityEvent`/`DataAccessEvent`/`PrivilegedActionEvent`/`ErrorEvent`) is append-only. Never add an UPDATE/DELETE code path against it outside the documented retention/legal-hold purge process. Write to it via `audit.usp_WriteAuditEvent`, not a direct `INSERT`, so redaction/shape rules stay in one place.
- Row-level security is real and enforced (`security.fn_tenant_access_predicate`, `SESSION_CONTEXT('TenantId')`) — any new HTTP request path must go through `TenantSessionContextMiddleware` (or call a stored procedure, which sets its own session context) before querying an RLS-protected table, or the query will silently return zero rows.
