# Master Management — Gap Analysis

> Title: Master Management Gap Analysis | Version: 1.0 | Owner: [TENANT_CONFIGURATION_REQUIRED — Engineering] | Status: Draft (Phase 1 inspection only — no code changed) | Last reviewed: 2026-09-09 | Next review: [TENANT_CONFIGURATION_REQUIRED] | Reviewers: Engineering, Security, DBA

## Purpose and scope

This document is the required Phase 1 deliverable before any Administration/Master-Management code is written. It records, from direct inspection of the real DDL/seed scripts and the real backend/frontend code — not from any prior documentation, which is known to drift — exactly what schema, API, Application-layer, UI, and permission scaffolding already exists for each of the 22 management areas requested, so that implementation does not invent schema, duplicate existing code, or contradict existing conventions.

**Sources inspected**: `src/HrAutomation.Infrastructure/Database/scripts/{01-09}-*.sql`, `Database/seed/{01-09}-*.sql` (every file read in full); `src/HrAutomation.Api/{Program.cs,Controllers/*,Auth/*,Security/*}`; `src/HrAutomation.Application/{Contracts/*,Security/*,Skills/*}`; `src/HrAutomation.Infrastructure/Persistence/{HrAutomationDbContext.cs,Entities/*,StoredProcedureExecutor.cs}`; `src/HrAutomation.Agents/Tan/*`; `openapi/hr-onboarding-api.openapi.yaml`; `tests/HrAutomation.Tests/*`; `src/HrAutomation.Web/src/{app/router/*, features/administration/*, hooks/usePermissions.ts, features/auth/*, types/*, components/common/*, mocks/*}`.

## Cross-cutting findings (apply to every area below)

- **No fine-grained permission enforcement exists in C# today.** Every current endpoint checks only `[Authorize]` (valid JWT) plus a per-skill hardcoded `RequiredRoles: string[]` list (`ISkill.RequiredRoles`, checked in `HrControllerBase.IsAuthorizedForSkill`). `AddAuthorization()` in `Program.cs` registers zero ASP.NET Core policies. The DB already has a real permission model (`iam.Permission`, `iam.RolePermission`) but **no C# code reads it**. Building real `permission.read`/`user.create`/etc. checks is new work required by every single endpoint in this module — see Decision D1 below.
- **No fine-grained permission model exists in React either.** `usePermissions.ts`'s `ROLE_PERMISSIONS` is an explicitly-labeled "best-effort UI approximation," hand-maintained, not fetched from the API. There is no `/v1/users/me/permissions` (or effective-permissions) endpoint today.
- **Only 3 of ~140 relevant tables have EF Core entities today**: `iam.[User]`, `iam.Role`, `iam.UserRole` (thin POCOs, not full column mirrors). Every other table this module touches (`iam.Permission`, `iam.RolePermission`, `iam.UserTenantAccess`, `iam.UserDepartmentAccess`, `iam.UserLocationAccess`, `iam.UserAuthenticationProvider`, `iam.AuthorizationPolicy(+Rule)`, all of `org.*`, almost all of `ref.*`, `workflow.WorkflowInstance/State/Transition/Task`, `onboarding.GreenForm*`, `ai.*`) needs a new EF Core entity class + `DbSet` + `OnModelCreating` mapping before any Application-layer code can query it.
- **RLS does not cover master/config tables.** `security.fn_tenant_access_predicate` is applied to 13 transactional tables only (Candidate, JobRequisition, Offer, etc.). None of `org.*`/`ref.*`/`iam.*` (the tables this module manages) have an RLS policy — tenant filtering for this module must be enforced entirely in the Application/EF Core layer (`WHERE TenantId = @ctx.TenantId` on every query), the same way `TenantSessionContextMiddleware` already sets `SESSION_CONTEXT` defensively but does not by itself protect these tables.
- **No stored procedures exist for generic master-data CRUD, role-permission grant/revoke, or generic approval-request creation.** Confirmed absent: `iam.usp_GrantRolePermission`, `iam.usp_SetTenantConfiguration`, `workflow.usp_CreateApprovalRequest`, `workflow.usp_RecordApprovalDecision`. The 33 stored procedures that do exist are workflow-critical, entity-specific actions (TAN/offer/employee-conversion lifecycle). Per the DDL scripts' own header comments, ordinary master-data CRUD is intended to go through EF Core, not new stored procedures — except where a table has a documented hard invariant (see `ref.NumberingRule` below).
- **A `/admin` route + 4 placeholder pages already exist** in the frontend (`features/administration/{AdminPage,AdminConfigurationPage,AdminRolesPage,AdminFeatureFlagsPage,AdminIntegrationsPage}.tsx`), all explicitly labeled read-only/placeholder pending a real API. These will be extended, not replaced from scratch.
- **`reporting` schema is empty** (zero views/procs) — any "configuration health summary"/"impact preview" screen needs new read queries built directly against source tables; there is nothing to reuse.
- **No `mcp` schema or `McpTool` table exists.** MCP tool metadata lives only as `ai.AiSkill.ToolAllowlistJson` (per-skill allowlist) and `ref.IntegrationConfiguration` rows tagged `IntegrationType='MCP'` at the provider level, not a per-tool level.

## Decisions required before/during implementation (see `DECISIONS_REQUIRED.md` for the register — new items to add)

- **D1 (Security/Architecture)**: how should real permission-checking be implemented — a new `IAuthorizationService` reading `iam.RolePermission` per request (cached?), ASP.NET Core policy-based authorization backed by a custom `IAuthorizationHandler`, or continuing role-string checks with a wider hardcoded map? This decision affects every endpoint below and should be made once, not per-area.
- **D2 (DBA/Architecture)**: `iam.AuthorizationPolicy`/`AuthorizationPolicyRule` are documented in the schema as "app-layer-evaluated ABAC metadata, not a SQL-enforced engine" — no evaluator exists in C#. Building §10 (Authorization policy management) requires designing and reviewing a rule-expression evaluator (the user's rules explicitly forbid letting UI users define arbitrary code/SQL) — this is non-trivial new design, not a CRUD screen.
- **D3 (Product)**: `ref.WorkflowDefinition/StateDefinition/TransitionDefinition` are seeded but **not wired to any live stored procedure** — editing them today would manage configuration that has no runtime effect on actual entity transitions (those are hardcoded in each entity's own status column + stored procedure). The Administration UI can CRUD these tables safely, but must not imply that publishing a new workflow version changes live TAN/offer/employee behavior — it doesn't, yet.
- **D4 (Security)**: MCP tool-level configuration (enable/disable per tool, write-capability classification) has no backing table. Options: extend `ref.IntegrationConfiguration` with tool-level rows, or treat `ai.AiSkill.ToolAllowlistJson` as the only manageable surface and document the MCP admin screen as skill-allowlist editing, not a tool registry. Needs a schema decision before `/admin/mcp-tools` can be built as literally specified.

## Priority summary (recommended build order, consistent with the user's own "Implementation Order")

- **P0** (build first — foundational, highest reuse, unblocks everything else): Organization master data (#2), Users (#3/#4), Roles (#5), Permissions read (#6), Role-permission assignment (#7), User-role assignment (#8), Audit reuse (#22), and — cross-cutting — Decision D1 (real permission-checking mechanism) must be resolved as part of this first batch since every subsequent endpoint depends on it.
- **P1**: User access scope (#9, with the BusinessUnit/Client gap flagged), Workflow/approval matrix definitions (#11, with the "not yet live" caveat documented in UI), Feature flags (#13), Interview rounds/feedback (#16), Document/verification config (#17/#18, conservative defaults), Offer templates/numbering (#20).
- **P2**: Tenant configuration (#1), Notification templates (#14), SLA policies (#15), Discrepancy config (#19), Authorization policy CRUD without the evaluator (#10).
- **P3 / needs a decision before scheduling**: MCP tool-level registry (#21's MCP portion — no table exists), Authorization policy rule evaluator (#10's "validate before publish" — no evaluator exists), full Tenant lifecycle CRUD beyond configuration (#1 — platform-scope, likely restricted to Platform Admin only, confirm blast radius with user first).
